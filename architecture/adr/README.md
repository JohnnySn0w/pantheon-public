# Pantheon ADRs

Architectural Decision Records for the org tier. Project ADRs live in their respective project repos; this directory is for decisions that span the hub or amend Pantheon's principles.

**See also:** the two other standards-tier surfaces:

- [`rfc/`](../rfc/) — RFCs (design specifications) that bridge an ADR's broad-strokes decision to implementer-hands-on-code. Established by [[ORG-092]] (2026-09-06). ADRs answer "which alternative and why"; RFCs answer "how does it work in detail — interfaces, invariants, state model."
- [`architecture/engineering-practices/`](../engineering-practices/) — HO-adopted methodology surfaces (moved from `notes/methodology/` under [[ORG-094]] / T-3472) below the goal-level ratify bar. Established by [[ORG-093]] (2026-09-06). Carries evolving practice — testing methodology, review methodology, dispatch methodology, verification methodology — that iterates HO-domain under D3/msg-3733 rather than through the operator ratify events.

**When drafting:** if the artifact captures a *decision*, it's an ADR (operator-ratified if it sits at goal level, otherwise HO-adopted; see the HITL field below). If it specifies the *interface / invariants / state-model implementation* the decision requires, it's an RFC. If it captures an evolving *practice discovery* HO adopts autonomously, it's a methodology pin under `architecture/engineering-practices/`.

## Numbering

`ORG-NNN`. Default starting at `ORG-001`. Separate from any project's ADR ranges. Project ADRs live in their project's repo (per the operator msg_1199 + msg_1200 + msg_1205):
- `echo-prismatic/adr/` — 1–199 reserved for operator-authored vault, 200+ for agent-authored.
- `pantheon-pwa/adr/` — 1–49 reserved for operator-authored vault (if/when), 50+ for agent-authored (established 2026-05-13 via T-0302; first entry ADR-050).
- Future project repos: file a sibling ADR establishing their own range; check existing ranges to avoid collision.

Pantheon (this directory) uses `ORG-NNN` exclusively; no overlap with project numeric ranges.

## HITL field (mandatory)

Every ADR carries one of:
- **Authored** — human-written by the operator. Implicit on principle amendments he writes directly.
- **Ratified** — agent-proposed, operator-accepted. Status line carries `Ratified: YYYY-MM-DD by the operator` and the channel where ratification happened (Telegram, terminal, GitHub PR).
- **Adopted** — agent-authored and adopted by the orchestrator under D3: the decision sits below the goal-level bar, so adoption is terminal (no the operator ratify step), ledgered, and surfaced in the digest (`rulebook/policies/trust-posture.md` §2026-06-11 amendment). This is the normal terminal state for orchestrator-initiated ADRs.
- **Autonomous** — agent-authored, not yet adopted or ratified (a draft in flight). Goal-level drafts wait here for the operator; below-goal drafts move to Adopted.

## When to write one

- Choosing between reasonable approaches with rationale that matters
- Defining or changing an interface (between tiers, with workers, with project orchestrators)
- Amending or extending a principle in `rulebook/principles.md`
- Resolving (or explicitly preserving — see P6) a tension
- Any decision at the D3 goal-level bar (the operator ratifies), and any below-bar ADR-tier decision worth recording (HO adopts; see the HITL field)

Do NOT write ADRs for: trivial refactors, styling, pure scaffolding, or things `BACKLOG.md` already tracks as work items.

## Format

Match the operator's vault-ADR style (see `echo-prismatic/adr/TEMPLATE.md` for the canonical shape, lifted from the operator's authored ADRs 001–011). Inline-header style, not a folder-per-ADR.

**Build-ticket label contract (T-1814, amended T-2806).** A ticket carved to build an ADR carries BOTH `build` and a namespace-correct join label in its frontmatter `labels:` list — `org-<NNN>` for `ORG-NNN` ADRs, `adr-<NNN>` for `ADR-NNN` ADRs, per the prefix→label-template map in `adr-namespaces.yaml` (repo root; a new prefix is a config add, not a code change). Both `org-NNN` and `adr-NNN` are accepted as join labels during the migration off the old adr-NNN-only convention. This is the join key `tools/ticket_grooming.py`'s ratified-unbuilt-ADR check uses to surface build gaps in the daily grooming digest.

**`build_disposition` (T-2806).** Every ADR frontmatter should carry `build_disposition: needs-build | no-build-needed | built`. `no-build-needed` and `built` both exempt an ADR from the ratified-unbuilt-ADR check — they mean "not an open build gap," whether because none was ever needed or because it's already shipped. `needs-build`, or the field being absent (pending backfill), makes the ADR eligible for the check.

**Zero-ticket backstop (T-2806).** The daily grooming check flags a ratified, needs-build ADR with **zero** matching build tickets in any state (inbox/active/done) — not only one with a stalled *open* ticket. A ratified ADR that silently never got a build ticket at all (the ORG-014 failure) is exactly the case this exists to catch. An ADR whose only matching ticket is already `done` is treated as already built and is not flagged.

**Prevent-at-creation (the operator, TG 7590; T-2806).** A landing ADR is rejected by `.github/workflows/adr-scoping-lint.yml` (`tools/adr_scoping_lint.py`) unless its frontmatter carries EITHER `build_disposition: no-build-needed`/`built`, OR a `scoping_ticket: T-NNNN`. Absence of `build_disposition` is treated as `needs-build` — a landing ADR must declare itself, not silently skip the question. The scoping ticket is expected to file the ADR's planning + follow-up build tickets on ratification. This is the structural primary; the zero-ticket backstop above is the safety net for anything that predates the rule or slips through (only genuinely NEW ADR files in a diff are checked — existing ADRs are grandfathered).

**Required fields — Appetite + Riskiest assumption ([[ORG-089]], Ratified 2026-09-06 by the operator via Telegram 9047).** Every non-vault ADR (agent-authored, i.e. every ORG-NNN in this directory + every ADR-NNN 200+ in project ADR directories) carries two additional required fields per the deference-heuristic RECORD-mode:

- **`appetite:` frontmatter integer 1-10** — the bet's appetite score, per the 3-sub-score rubric at `knowledge/episodic/2026-09-05-deference-heuristic-proposal/appetite-scale.md` (value + strategic alignment + reversibility, averaged).
- **§Appetite body section** — reasoning: what this is worth NOW, the ceiling against over-specification, explicit not-in-scope.
- **§Riskiest assumption body section** — the one unknown that would kill the bet + the cheap way to test it (the floor against under-viability).

Both fields become audit-chain evidence even when the operator overrides — the pass ran, the record shows it, alternatives-considered survive. See [[ORG-089]] §Decision + [[ORG-089]] itself as the worked example (dogfoods both fields). Grooming lint per [[ORG-089]] §Surface 4a-completeness flags ratified non-vault ADRs with empty or boilerplate values; legacy grandfathering by ratify-date (ADRs ratified before ORG-089 landing 2026-09-06 exempt).

**Ratifiable copies stay clean of review clutter (the operator TG 9065, 2026-09-06).** The copy of an ADR handed to the operator for ratification — whether landed on main, mailboxed, or attached to a chat — must be free of review-cycle content. REBOUND logs, finding→amendment tables, round-by-round review notes, provenance-of-intermediary-reviews chains, and other cutting-room artifacts belong in companion `notes/<date>-<slug>-review-history.md` files or ticket transition logs, NOT in the ratifiable ADR body. Intermediary drafts (agent branches, review passes, mailbox drafts to peers) may carry review-artifacts freely for the review flow; the formal ratify-package is the clean copy. Worked examples: `notes/2026-09-06-org088-review-history.md` (ORG-041 REBOUND log + typed-contracts pseudo-code + build-tranche enumeration relocated from ORG-088 body); `notes/2026-09-06-org072-normative-additions-relocated.md` (build-tier A-item detail relocated from ORG-072 per the operator RATIFY-WITH-RELOCATION TG 1786-1791). Companion to the altitude rule: ratifiable ADR = design decisions + intent; build-tier detail (mechanics, numerics, method signatures, per-consumer enumeration, state machines) also lives in build tickets or referenced notes.
