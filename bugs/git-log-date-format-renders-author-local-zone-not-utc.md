## Symptom

A commit appears to land *hours* before it actually did, and any reasoning that compares it to a
process start time, a file mtime, or another agent's timestamp inverts.

```
$ git log -1 --format='%h %ad' --date=format:'%H:%M:%SZ' 91c4b8e8f
91c4b8e8f 15:28:12Z          # <-- claims 15:28 UTC

$ TZ=UTC git log -1 --format='%h %ad' --date=format-local:'%Y-%m-%dT%H:%M:%SZ' 91c4b8e8f
91c4b8e8f 2026-07-28T20:28:12Z   # <-- actually 20:28 UTC, five hours later
```

## Cause

Two independent traps that compose:

1. **`--date=format:` renders in the commit's own author-local zone**, not UTC. (`format-local:`
   is the variant that respects `TZ`.)
2. **The trailing `Z` was a literal character in the format string.** `strftime` has no `Z`
   directive here, so it is emitted verbatim — the output *asserts* UTC in exactly the case where
   it is not. The label is generated by the person who is wrong.

⚠ **A repo can carry mixed offsets**, so this is not a constant you can correct for once. Verified
in `pantheon-config` — two commits seven minutes apart:

```
91c4b8e8f  aI=2026-07-28T15:28:12-05:00
14d5d6db3  aI=2026-07-28T20:21:21+00:00
```

Also note `%ad` is the **author** date (rewritten by rebase/cherry-pick, and settable via
`GIT_AUTHOR_DATE`). For "when did this land on this branch", `%cd`/`%cI` (committer date) is usually
the field you want.

## Fix

```bash
# Preferred — explicit offset, no formatting decisions:
git log -1 --format='%h %cI' <ref>          # 2026-07-28T20:28:12+00:00

# If you need a rendered UTC string:
TZ=UTC git log -1 --format='%h %cd' --date=format-local:'%Y-%m-%dT%H:%M:%SZ' <ref>

# Or let git do it:
git log -1 --format='%h %cd' --date=iso-strict-local <ref>   # with TZ=UTC
```

Rule of thumb: **never hand-append a zone label to a git date.** If the format string contains a
literal `Z`, the output is an assertion you have not checked.

## Why this one is worth a catalog entry

The failure is *silent and self-confirming*. In the incident below, the same five-hour error also
made a `_lease.py` clone look like it "lagged three hours behind its commit" — that apparent lag was
purely UTC-minus-local, and it was then cited as **independent corroboration from a different kind
of artifact (a file mtime, not a git field)**. Two sources agreed because one bug had written both.

⇒ **When a discrepancy appears, confirm it in a unit the suspect computation cannot influence.**

The wrong reading produced a confident, well-evidenced conclusion — that two `mailbox_mcp` processes
were *post*-fix and the whole fleet had been dating arming against the wrong file — which inverted a
live safety question (T-2236). It was caught only because **two peers' accounts contradicted each
other**: one agent's message said a PR had merged at a time the misread placed three hours after the
merge.
