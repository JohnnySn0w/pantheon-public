# Lessons

Conceptual lessons — abstracted insights that sit BETWEEN concrete events (incidents, kerfuffles, dispatches) and durable rules (principles, directives). Distinct from neighbors:

- `incidents/` — per-event postmortems (what happened, why, structural prevention).
- `bugs/` — technical-symptom-with-surgical-fix entries (small, looked-up via grep).
- `rulebook/directives.md` — Pantheon's scoped + dated rules (D1-D12 ratified).
- `rulebook/principles.md` — Pantheon's durable Source-of-Will rules (P1-P6 ratified).
- `adr/` — architectural decisions (org-tier amendments).
- `sop/` — operational procedures (how to do X correctly + remediation playbooks).

Lessons are the **abstracted insight layer**. Reading a lesson tells you "this is the pattern; here's what it implies for how we design SOPs / directives / principles / future arcs." A lesson may eventually become a directive (D-class) or a principle (P-class) if its design implications harden, or it may inform multiple SOPs without itself becoming a rule. The point of having this category is that not every insight is rule-shaped, but many insights are still durable + reusable + worth indexing.

## When to add

Add a lesson when:
- Multiple incidents / cycles / dispatches cohere into a pattern that's bigger than any one of them.
- An insight earns a name (the kind of name that re-surfaces in design conversations).
- An external precedent (military doctrine, cybernetics, distributed systems theory) maps usefully onto a Pantheon discipline.
- An operator-articulated theory (the operator's intuitions; see `operator-theories/`) wants empirical tracking over time.

Don't add a lesson when:
- It's a single event — that's an incident, not a lesson. (Incidents may seed lessons later, but the seeding is a separate authoring step.)
- It's a technical gotcha with a surgical fix — that's `bugs/`.
- It's a rule about how Pantheon operates — that's `rulebook/directives.md` (or, for higher-stature: `rulebook/principles.md`).
- It's a procedure — that's `sop/`.

## Per-lesson file shape

Per T-0158 ratification (the operator msg_863):

```markdown
# <Pattern name — one line, distinctive>

**Date authored:** YYYY-MM-DD
**Author:** Orchestrator (Orchestrator) [or attribution if the operator / external]
**Status:** Drafted / Ratified / Superseded
**Re-evaluate when:** <event or date trigger>

## Observation

The phenomenon. What you see across multiple cases. State it concretely enough that
a future reader can recognize the pattern when they see it again.

## Grounding

The cases this lesson abstracts from. Cite ledger entries, incident reports, kerfuffle
catalogs, ADRs, telegram messages, external research notes. Lessons without grounding
are just opinions.

## Design implications

What this means for how Pantheon designs going forward. Concrete: which SOPs would
the lesson revise? Which directives would it support amending? Which future arcs
should be designed differently because of this?

## Open questions

What's not yet known. The lesson's frontier — empirical or conceptual.

## Cross-references

- Principles / directives / ADRs that touch.
- Incidents + bugs + SOPs that ground or cite.
- Tickets that filed-from or feed-back.
```

## Authoring discipline

- HO drafts under D2 (hand-curated).
- The operator ratifies per-lesson at surface time. Substantial lessons (e.g. ones that recommend a new directive) get explicit Telegram surfacing; lighter ones land + get reviewed at periodic spine sweeps.
- Re-evaluation of any lesson happens when its design implications drift OR when a new incident contradicts.
- Lessons feed UP — they're the structural input layer for directive amendments, principle ratifications, SOP revisions.
- Information-inflow bubble-up methodology (how a lesson promotes into a directive promotes into a principle) is itself a lesson — see `operator-theories/` (work-in-progress) and T-0168 (inflight ticket).
