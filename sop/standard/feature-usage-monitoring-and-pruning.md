# Feature-usage monitoring and pruning

**Status:** Drafted 2026-07-28 by Recovery at the operator's direct request (Telegram 16:52Z): *"we need an sop on how to setup monitoring for feature usage to prune features we don't actually use. veneration seems like it both was dumb and was never used."* Written immediately after decommissioning the-ancestor daemon (T-2214), so Part 1 is the procedure that case actually ran, not a reconstruction. Adopted under principles-as-ratification (methodology, below the goal-level bar per amended D3); the operator override-available.

## Why this exists

We build faster than we retire. A feature that is never called does not announce itself —
it keeps passing its tests, keeps its process alive, keeps its unit `active`, and bills us
memory, alerts, and operator attention forever. The veneration/resurrection service ran for
**45 days with zero production callers** and its only observable output in that period was
the alerts generated by its own idleness — a boot wedge, a liveness page, and an OAuth
re-login that cost the operator a browser round-trip on an incident day.

## Two axes, and the second is the one we missed

**Axis 1 — UNUSED.** Nothing calls it. Measurable statically and behaviourally (Part 1).

**Axis 2 — UNECONOMIC.** It *is* called, or could be, but a cheaper path does the same job.
Veneration failed here too: per the operator, resurrecting a session costs **more tokens than
simply scraping the dead session from the Chronicle**. A wired caller would still have been
the wrong choice.

Recovery's pre-decommission analysis found Axis 1 only. The operator supplied Axis 2 from memory —
which is precisely the failure this SOP exists to prevent, because that number lived in a
conversation and not on a durable surface. **Record the cost comparison at build time or it
will not survive to the pruning decision.**

A feature must clear BOTH axes to be worth keeping. Usage > 0 does not justify a feature
whose cheaper alternative already exists.

## Part 1 — Measuring an existing feature (the forensic path)

Ranked strongest to weakest. **Signal 1 alone is usually decisive**; the rest corroborate.

### 1. Static: does a production caller exist? (strongest)

Grep the repo for the feature's entrypoint token — the payload `type`, the function, the
protocol verb — and classify every hit as *implementation*, *test*, *doc*, or **caller**.

```
git grep -ln '<entrypoint-token>'
```

For veneration the token was `resume_request`, and it appeared in exactly two files:
its own module and its own test. **No caller existed anywhere.** That single measurement
decided the case.

- Use `git grep`, not `grep -r` — the latter counts binary `__pycache__/*.pyc` and inflates
  the result. If you must scan the filesystem, clear `__pycache__` first (there is usually
  more than one such dir; find them all) and **say which surface you scanned**.
- Docs, ADRs and *done* tickets referencing the feature are **not** callers. A feature can be
  thoroughly documented and completely unreached.

### 2. Behavioural: what does its own data surface say, with dates?

Every feature that does work leaves residue — processed mail, log lines, state files, output
artifacts. Count it **and date it**. A raw count answers "ever?"; the dates answer "still?".

Veneration's inbox held exactly 2 messages for all time, both from the same sender, both
45 days old. Its last substantive session transcript was 6 weeks stale; the current day's
transcript was 1,952 bytes, consisting entirely of the boot banner and an operator `/login`.

### 3. The natural experiment (strongest when available, and it is free)

**If the feature was broken for a period and nothing noticed, that is a usage measurement.**
Do not discard an outage as merely an incident — mine it.

the-ancestor's session was auth-dead *and* boot-wedged for hours on 2026-07-28 while all
fleet mail flowed normally throughout. Nothing depended on it. That fact was worth more than
any static analysis, and it cost nothing to collect because the outage had already happened.

### 4. Cost, so the tradeoff is explicit

Resident memory, token consumption, alert volume, and operator interrupts. State cost against
a box's actual headroom, not in the abstract: 348 MB reads as trivial until you note the host
hit 100% memory that afternoon with swap already half-consumed at baseline (T-2213).

## Part 2 — Instrumenting new features so this is never forensic again

The measurements above are archaeology. They worked, but they cost a full investigation.
For anything new that runs unattended:

1. **Emit a usage counter at the entrypoint.** One line — timestamp, feature, caller — to the
   feature's state dir. Then "is this used?" is a `tail`, not an investigation.
2. **Record the cost comparison in the design ticket**, with numbers, at the moment the
   alternative is still fresh. This is the Axis-2 gap; the veneration token math existed in
   someone's head and nearly did not survive to the decision.
3. **Name the intended caller in the ticket.** If a feature ships with no named caller and no
   ticket to wire one, it has shipped dead. Say so at review time, not 45 days later.
4. **Give unattended features an expiry review date** (`--not-before` self-addressed ticket,
   90 days). Absent a forcing function, nothing is ever revisited.

## Part 3 — Deciding, and decommissioning safely

### Separate the SUBSTRATE from the SERVICE before removing anything

The single largest over-deletion risk. In the veneration case the *account* `the-ancestor`
owns `/home/the-ancestor/mailbox`, which is the entire fleet's inter-agent mail hub, while
the *claude session* on that account was the unused resurrection service. They share a name
and are not the same thing. Removing the session was correct; removing the account would
have taken the whole fleet's comms down.

**Ask explicitly: what is load-bearing here, and what merely lives next to it?**

### Decommission procedure

1. **Disable dependent monitors in the SAME change.** A liveness monitor left armed against a
   deliberately stopped service manufactures exactly the alert noise the pruning was meant to
   remove. (Same class as the T-0536 wire-hook-update-allowlist-together rule.)
2. **Prefer `disable --now` over deletion.** Reversible with one command; keeps the option open.
3. **Do not delete accounts, data directories, or message stores** in a service-pruning change.
   Separate decision, separate diff.
4. A unit with no `[Install]` section will report that it cannot be disabled — that is
   expected for timer-activated units, not a failed step. Disable its **timer**.

### Verify after, against the thing you were afraid of breaking

Not "the unit is stopped" — that only proves you did the thing. Verify the capability you
were worried about still works. For the hub: `st_nlink` oracle for box count, all boxes
present by explicit name, and a real send→consume round-trip. State health explicitly.

## Traps

- **Tests passing is not usage.** A feature can be fully green, fully documented and fully
  unreached. Green tests measure the artifact, never its demand.
- **Process alive is not usage.** `is-active` and `pgrep` report that something *can* run.
- **A count without a predicate is not evidence.** Say what you counted and on which surface;
  two people scanning "the same thing" with different predicates get different numbers.
- **Do not infer death from silence alone.** Seasonal, on-demand and disaster-recovery
  features are legitimately idle. Signal 1 (no caller) is what separates *idle* from *dead* —
  a DR feature has a caller wired even if it has never fired.
- **Documentation is not a caller**, and a feature's own SOP is not evidence it is used. When
  pruning, retire the feature's SOP in the same change or the index keeps pointing at a
  decommissioned capability.

## Cadence

Quarterly sweep of unattended services: for each, run Signal 1. Anything with no production
caller goes on a list with its cost, and the list goes to the operator as a digest — the decision
to retire a capability is goal-level (which projects exist / what they are for), so agents
measure and recommend; the operator rules.

## Autonomous-vs-bubble-up D3 placement

**Measuring** usage is unrestricted — read-only, do it freely. **Recommending** a prune is
below the bar; produce the analysis and a digest. **Executing** a decommission is goal-level
(it changes what exists) and needs the operator's word — as T-2214 did. Reversibility does not
downgrade it; "which capabilities exist" is his call regardless.
