# sop/standard/

Procedural "how to do X correctly" SOPs. Each entry is a runbook for an operation that recurs frequently enough to warrant codification.

## Project-level SOPs (in each project repo)

Project-specific operational runbooks live in the PROJECT repo's `sop/` dir, not here — domain knowledge stays next to its code; this index is the discovery pointer (convention ratified by the operator 2026-07-04, TG 4593). Check the project's `sop/` before debugging or operating that project's components:

- **echo-prismatic** `sop/` — [`debugging-conversation-pipeline.md`](https://github.com/example-org/echo-prismatic/blob/main/sop/debugging-conversation-pipeline.md) (tap-first stage elimination, instruments, known failure signatures; journald is a trap for echo). More to come: audio-IO/AEC debugging (post T-1373 redesign).
- Other repos: none yet — when a project grows its first SOP, add its line here.

## When to add

- A procedure has stabilized (HO has done it ≥3× the same way).
- Multiple agents would benefit from following exactly the same steps.
- Re-deriving the discipline each time is costing real bandwidth.

## When NOT to add

- One-shot procedures (→ ticket body).
- Procedures that vary substantially per case (→ keep in agent judgment).
- Failure-mode discipline (→ `sop/remediation/` instead).

## File shape

See `sop/README.md` §Per-SOP file shape §standard/ for the canonical template:

```
# <SOP name>

## When to use this
## Procedure
## Common failure modes
## Boundary
## Cross-references
```

## Per-SOP adoption

HO (or the authoring seat) drafts and adopts, then records it in a ledger entry and a digest line. An SOP is methodology, below D3's goal-level bar (amended 2026-06-11, the operator msg 3733/3735), so there is no ratify-ask, and the status line reads `Adopted <date> by <author>`. An SOP that would set a goal-level rule goes to the operator. Entries he ratified earlier keep `Ratified`. See `sop/README.md` §Authoring + adoption flow.

The hand-curated "Founding entries" / "Out-of-band entries" lists that follow are retained for their curated descriptions + historical grouping (founding set, migration provenance) — any status text in them is **historical and not maintained**; do not rely on it.
