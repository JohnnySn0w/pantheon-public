# Auto-commit collision on id-class

**Status:** **Ratified 2026-06-08 by the operator.** Draft 2026-05-13 (T-0196 #9 of 9; pending the operator ratification per T-0157 framework).

## Failure shape

Two (or more) auto-committers operating in parallel race at the same identifier-class boundary — most commonly the ticket-id (`T-NNNN`) or a lane-path (`tickets/<state>/T-NNNN.md`) — and produce a collision: duplicate IDs, parallel files for the same ID, or audit-chain duplicates referencing distinct work under one name. Surfaces post-push when the second writer's local state predated the first writer's push; or surfaces in retrospective scan when a second-tier consumer (`tools/ticket.py _find_ticket`, the inbox-consumer, ratification queue readers) reads two artifacts where the schema expects one.

Distinct from `routing-mis-routing-to-team-lead` (sender-side address error; one canonical artifact, wrong recipient). This pattern produces *two artifacts at the same address* — the schema's uniqueness invariant is violated.

Distinct from `claimed-prior-approval` (worker fabricates approval; single artifact, false framing). Auto-commit collisions produce real artifacts from real auto-commit runs, both legitimate-in-isolation; the failure is the parallelism itself.

Variants:

- **ID-allocation race (ticket).** Two auto-committers (HO + Recovery, or HO + Specialist, or two parallel HO subprocess) each run `ticket.py file` at the same id-class boundary; each scans local state, sees `T-NNNN` is the next free ID, allocates it. The first to push wins the canonical slot; the second pushes a duplicate-ID commit OR (worse) push-races and both end up on `origin/main` if the fetch-then-scan-both-trees discipline isn't in place. **Canonical precedent:** T-0042 collision 2026-05-03 + T-0066 collision 2026-05-04 (both fired within the same 24h before the structural fix landed via T-0068).
- **Lane-path collision (file).** Both writers target the same `T-NNNN` but the schema's lane-by-directory convention (`tickets/{inbox,active,blocked,done}/`) allows the same filename to exist in multiple lanes simultaneously. The second writer's edit lands in the wrong lane (typically `inbox/` because that's the default for `>` append fallback patterns) instead of appending to the canonical file in `active/`. Surfaces because `ticket.py _find_ticket` walks STATES in order; the misdirected stub in `inbox/` shadows the canonical file in `active/`. **Canonical precedent:** T-0188 2026-05-10 — Recovery's `tickets: T-0188 + T-0185 — append j17 test instance key` commit 651f431 wrote a 1-line stub at `tickets/inbox/T-0188.md` instead of appending to the active version at `tickets/active/T-0188.md`. Salvaged + cleaned 2026-05-13.
- **Ledger-id collision.** Two auto-committers write entries with the same `id` field in `ledger/2026.jsonl` because they both used a same-second timestamp + same action-name template. Less common because the timestamp resolution is per-second and the action-name typically carries enough discriminant; surfaces when two cron-fired tools both fire at the same minute-mark.
- **Cross-repo ID-class collision.** A ticket's `ratifiable_files` field references multiple repos (per T-0291 schema); two auto-commit cycles in different repos race on the same logical-id resolution (e.g., MX-001 in revenue-project + a sibling-named doc in pantheon-config). Speculative variant; no precedent yet but the schema admits it.
- **Watch-report slug collision.** Specialist's `watch_runner.py` auto-commits reports under `knowledge/watch/reports/<date>/<slug>.md`; two same-day reports on overlapping topics produce slug collisions. Surfaces when the slug-generation logic doesn't carry enough discriminant (e.g., two reports both slug to `context-management`).

Characteristic signal HO sees: a `ticket.py` or `git push` command fails with non-fast-forward / merge-conflict at the collision boundary, OR a retrospective scan surfaces two files at the same canonical address. The structural fix (T-0068) makes ID-allocation races fail loudly at filing time rather than silently at push time; lane-path collisions still surface via the `_find_ticket` shadowing pattern and need retrospective scan.

## Precedent cases

- **2026-05-03 — T-0042 first collision** (per ledger entry `2026-05-04T23:14:00Z-001`). B8 wind-down filed 17:52Z + B9 design filed 21:55Z; both via `ticket.py file` CLI; both got ID T-0042 because `_next_ticket_id` scanned only local state. The operator flagged via msg_572 audit check. Renumbered the older B8 wind-down (commit `1095bfb` → `31484be` → eventually `01759ef` after a second sub-collision).
- **2026-05-04 — T-0066 second collision** (same ledger entry). Recovery filed T-0066 documenting an `activity_digest.py` unicode-escape bug; concurrently HO's B8 wind-down (renumbered above) also tried to land as T-0066 because the same `_next_ticket_id` bug was still live. Renumbered HO's wind-down a second time (T-0066 → T-0067, commit `01759ef`). All four cross-references updated each renumber (BACKLOG.md / notes/auto-resume.md / tickets/README.md / ticket frontmatter).
- **2026-05-05 — T-0068 structural fix landed** (commits `54e6632` + `6a44483`). `_next_ticket_id` rewritten to fetch origin then scan both local + origin/main:tickets/ via `git ls-tree`. `cmd_file` gains bounded N=3 retry on non-FF push (delete file + `git reset HEAD~1` + re-allocate). 8 new tests covering all 5 race scenarios. The race-condition-allowing-duplicate-IDs class of failure is structurally retired post-fix.
- **2026-05-10 → 2026-05-13 — T-0188 lane-path collision.** Recovery's append commit `651f431` wrote a new 1-line file at `tickets/inbox/T-0188.md` instead of appending to the canonical `tickets/active/T-0188.md`. The misdirected stub shadowed the canonical via `_find_ticket`'s STATES-order walk. Surfaced on HO's inbox scan 2026-05-13; salvaged content into active/'s transition log + git rm'd the stub (commit `828a2c0`). Lane-path collision class is NOT structurally retired by T-0068 — same-ID-different-lane is allowed by the schema (e.g., transient states during `git mv`); the failure is the *write path* not the ID allocation.

The pattern is structurally distinct from the worker-tier and orchestrator-tier discipline failures: the collision arises from parallelism at the *substrate* level (multiple cron'd auto-commits hitting the same git tree). Discipline-tier rules don't help; the remediation is mechanical (renumber or salvage) and the structural fix lives at the tooling layer (T-0068 for ID race; lane-path collision has no structural fix yet beyond write-discipline).

## Recommended remediation

Ranked by precedent + cost.

*Terms used below.* "ID-class" = the namespace at which uniqueness is required (ticket-id, ledger-id, watch-report-slug). "Canonical artifact" = the artifact that retains the contested address; "loser" = the artifact whose address gets reassigned or whose content gets folded into the canonical. "Cross-references" = every file that names the contested ID — BACKLOG.md, notes/, tickets/README.md, parent_ticket fields in sibling tickets, ledger entries, commit messages.

**Path A — Renumber the loser + audit cross-references.** *Default for ID-allocation races (T-0042 / T-0066 class).*

- HO does: (1) determine which artifact retains the contested ID — typically the one filed first by `created` timestamp, OR the one with more downstream references (parent_ticket links, ledger citations, cross-doc mentions); the loser gets the new ID. (2) Allocate a fresh ID via `ticket.py file` against the current origin state (T-0068 fix ensures fresh allocation). (3) `git mv` the loser's file from `T-OLDID.md` to `T-NEWID.md` in whichever lane it occupies. (4) Update the loser's frontmatter `id:` field. (5) Audit-grep for `T-OLDID` across the repo + every cross-referencing repo; update each mention. (6) Commit the renumber as one atomic change with a clear message naming the collision and the renumber direction.
- Why: ID-allocation races produce two real artifacts both worth preserving (different work, different `Ask` bodies); the conflict is only over the address. Renumbering preserves all the work + maintains the audit chain via the renumber commit's clear message.
- Expected outcome: both artifacts have distinct IDs; all cross-references resolve; future readers can trace the renumber via the commit message.
- When to escalate: if the loser's downstream references are numerous (>5 ledger entries, multiple cross-repo citations) and the renumber audit would touch hand-curated docs in vault (`adr/`, `notes/`, `incidents/`), bubble up to the operator before applying — the audit-chain disturbance crosses the autonomy bar.

**Path B — Salvage content into canonical + delete the loser.** *Default for lane-path collisions (T-0188 class).*

- HO does: (1) determine which artifact is canonical — typically the one with frontmatter + full ticket body; the loser is a stub or stray append. (2) Fold the loser's content into the canonical's transition log (or appropriate body section) with an inline provenance note: `(Salvaged from misdirected append at <path> — <originating-commit> wrote to <wrong-dir> instead of appending to this <canonical-dir> file; inline-folded here on <date>.)`. (3) `git rm` the loser. (4) Commit as a two-part change naming both the salvage and the lane-path-collision class. (5) Confirm `_find_ticket` resolves cleanly (single file at canonical address; no shadow).
- Why: lane-path collisions don't produce two real artifacts worth preserving — the loser is typically a misdirected append (single transition-log line, no semantics). Salvage-then-delete is information-preserving; the alternative (leaving both files) creates `_find_ticket` shadow ambiguity that breaks downstream tooling.
- Expected outcome: single canonical artifact at the contested address; downstream tooling resolves cleanly; the salvaged content is preserved verbatim with provenance.
- When to escalate: if the loser file has more than transient content (full frontmatter + body, suggesting an independent ticket that mis-collided), treat it as ID-allocation race (Path A) instead — the loser deserves its own ID.

**Path C — File a structural-prevention follow-up sibling ticket.** *Apply after Path A or B when the root cause is a reproducible tooling gap.*

- HO does: file a sibling ticket (target=orchestrator if HO can fix tooling; target=recovery if it crosses Recovery's sudo scope) naming: (a) the collision class (ID-allocation race vs lane-path collision vs ledger-id collision vs slug collision); (b) the tooling gap that allowed it (e.g., `ticket.py` writes new file without checking destination dir's lane-canonical-for-this-id; `watch_runner.py` slug-generator lacks topic-discriminant); (c) the structural fix shape (the T-0068 fetch-then-scan-both-trees pattern is the reference for ID races; lane-path collisions need a `_find_ticket` pre-write hook or similar). The structural fix lives in the sibling ticket; this SOP's primary action stays at remediation.
- Why: collisions that don't get a structural fix recur. T-0068 retired the ID-allocation race class; lane-path collisions remain live until a similar structural fix lands. The sibling ticket carries the structural work; this SOP's remediation paths are the "until then" mechanical fix.
- Expected outcome: structural-prevention ticket filed with `parent_ticket: T-NNNN-of-the-collision-incident`; sibling enters the normal inbox flow; eventual fix retires the collision class from this SOP's scope.
- When to escalate: structural-prevention tickets that touch `tools/ticket.py` (the substrate of the ticket system) are policy-touching at the tooling layer. File the sibling; brief explicitly notes it touches ORG-003 substrate; reviewer pre-flight catches if the fix crosses into ADR-tier amendments.

## Autonomous-vs-bubble-up D3 placement

- **Paths A, B: HO-autonomous.** Both fall under `trust-posture.md` auto-approve scope ("ticket lifecycle transitions via tools/ticket.py" + "filing follow-up tickets when scope expands beyond a closing ticket"). The renumber audit (Path A) is mechanical; the salvage-then-delete (Path B) is information-preserving with clear provenance. **D3 wait-time-bound: collision remediation fires on detection; no inflight gate.**
- **Path A escalation case:** if renumber audit would modify hand-curated vault docs (adr/, notes/, incidents/, principles.md, directives.md, CLAUDE.md), bubble up before committing the audit. The audit-chain disturbance crosses the modify-hand-curated-docs threshold per trust-posture.
- **Path C: HO-autonomous for filing the sibling ticket.** Implementation of the structural fix follows the normal cycle (plan-first dispatch if non-trivial; HO-direct if a small tooling tweak). The fix itself stays inside D8 HO-direct edit-loop threshold for small surfaces.
- **D3 calibration check.** Lane-path collisions surface less frequently than ID-allocation races did (pre-T-0068); the SOP's primary user is HO doing retrospective scan after observing `_find_ticket` shadow ambiguity OR after a `git push` non-FF failure on a ticket commit. Two or more collisions in one week from the same root cause warrants accelerating Path C — sticky-belief threshold per D8.

## Upstream prevention

This SOP is the *post-collision* remediation. The *pre-collision* discipline lives at three layers:

1. **Tooling-layer prevention.** T-0068's fetch-then-scan-both-trees pattern in `_next_ticket_id` retired the ID-allocation race class. Equivalent structural fixes for lane-path collision (a `_find_ticket` pre-write hook, or a `ticket.py append` subcommand that locates the canonical file first), ledger-id collision (per-microsecond timestamps + action-name uniqueness check at write time), and watch-report-slug collision (slug-generator with mandatory topic-discriminant) are SOP-tier candidates for Path C follow-ups.
2. **Write-discipline at the auto-committer.** Every auto-committer (`ticket.py`, `watch_runner.py`, `ticket_grooming.py`, `pantheon_config_sync.py`, future tools) should: (a) fetch origin before allocating any unique-id; (b) when appending to an existing artifact, locate the canonical file via `_find_ticket`-equivalent logic, not assume the inbox/ default; (c) fail-loud on push race rather than silently shadowing. Brief-language for any implementer touching auto-commit code includes this discipline.
3. **Retrospective-scan in HO's smell-test rotation.** HO scans for collision signals as part of the per-turn smell-test when working in `tickets/`: (a) `find tickets -name "T-NNNN.md" | wc -l` should be 1 per ID; (b) `git log` of recent ticket commits should not show same-ID auto-commits within minutes of each other from different actors. Lightweight; runs in the same scan that catches the active-team worker silence pattern.

Until the lane-path collision structural fix lands, this SOP fires every time a stub-in-wrong-lane is observed in retrospective scan.
